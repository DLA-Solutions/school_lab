Bem-vindo(a) ao School Lab

School Lab é um SaaS de gestão para escolas particulares brasileiras — um monorepo com API em Rails, SPAs em React e app mobile em React Native. Este guia te leva da arquitetura até a entrega da sua primeira task.

01 Visão geral do produto

O produto atende escolas particulares: direção, secretaria, professores e responsáveis (guardians). A interface do produto é em pt-BR, mas todo o repositório — código, API, docs, nomes de branch — é em inglês. Português só é usado em textos exibidos ao usuário final (i18n) e em exceções de domínio documentadas no glossário.

isolamento

Cada escola só enxerga seus próprios dados (school_id) e cada família só enxerga seus próprios registros — mesmo rigor de isolamento para ambos.

lgpd

O produto lida com dados de crianças. Acesso mínimo, consentimento do responsável como base legal, cuidado extra com dados sensíveis (saúde, ocorrências).

02 Arquitetura do monorepo

Um único backend serve três frontends. Nenhum cliente duplica regra de negócio — tudo que é regra vive na API.

frontend/app

03 Sua primeira task

Escolhida por três motivos: é só frontend (não mexe em Rails), a API que ela consome já está em produção, e os critérios de aceite já estão escritos.

Issue #202

Tela de listagem e edição de "papéis" (role templates)

Desbloqueada

Toda escola tem papéis (role templates) que definem o que cada funcionário pode fazer: Direção, Secretaria, Coordenação, Professor — mais papéis customizados que a própria escola pode criar (ex: "Recepção"). Sua task é construir a tela onde o dono da escola vê esses papéis e edita as permissões de um papel customizado.

Givenum(a) dono(a) de escola com permissão manage_people
Whenele(a) abre as configurações de papéis
Thena tela carrega GET /schools/:id/role_templates e mostra papéis de sistema e customizados com seus conjuntos de permissão
Givenum papel customizado (não-sistema)
Wheno dono altera permissões e salva
Thena tela chama PATCH /role_templates/:id e exibe affected_memberships_count retornado na resposta
Givenum papel de sistema (ex: "Direção")
Whententam excluí-lo
Thena UI impede a ação ou mostra o erro cannot_delete_system_template vindo da API

04 Regras de negócio que a tela precisa respeitar

Extraídas de docs/prds/identity-and-onboarding/permissions.md. Não é preciso implementá-las de novo — a API já aplica tudo isso — mas a UI precisa refletir esse comportamento com fidelidade.

D2 — sistema vs. customizado

director, secretary, coordination e teacher são papéis de sistema (is_system: true), provisionados automaticamente por escola. Escolas podem criar papéis customizados combinando permissões do catálogo.

UI: papéis de sistema são somente leitura — sem editar nome/permissões, sem excluir.

PD-1 — propagação

O papel de um funcionário é um ponteiro, não uma cópia. Editar um papel afeta imediatamente todos os funcionários que o usam — recalculado a cada request.

UI: por isso o PATCH retorna affected_memberships_count, que precisa aparecer para o dono antes/depois de salvar.

PD-2 — overrides separados

Permissões extras por pessoa (overrides) ficam em outra tabela e nunca são sobrescritas silenciosamente ao editar um papel.

Fora do escopo desta task — overrides têm tela própria (issue futura, W2).

BR-P01

O papel de membership school está sendo renomeado para staff no código. Na UI, a escola continua sendo chamada de "Escola" e a equipe interna de "Equipe" (não confundir os dois conceitos).

escopo

Ação: POST /role_templates/:id/clone permite duplicar um papel existente — útil na UI como atalho para "criar customizado a partir de um de sistema".

autorização

Listar exige manage_people; criar, editar, excluir e clonar exigem ser dono(a) da escola (is_owner). A API já garante isso — a UI deve esconder/desabilitar ações para quem não é dono.

⚠️
Cuidado com o "blast radius": como o modelo é ponteiro (PD-1), editar o papel "Secretária" errado pode mudar o acesso de várias pessoas de uma vez. Sempre mostre affected_memberships_count antes de confirmar um PATCH — é a mitigação de risco documentada no PRD.

05 Contrato de API que você vai consumir

De docs/api/v1/identity-onboarding.md. A API já está implementada e mergeada — trate este contrato como fixo; se algo não bater, é a UI que precisa se ajustar, não a API.

MétodoRotaDescrição
GET/schools/:school_id/permission_definitionsCatálogo de permissões disponíveis na plataforma
GET/schools/:school_id/role_templatesLista papéis da escola — requer manage_people
POST/schools/:school_id/role_templatesCria papel customizado — somente dono(a)
PATCH/role_templates/:idAtualiza papel — resposta inclui affected_memberships_count
DELETE/role_templates/:idExclui papel customizado — bloqueado para papéis de sistema
POST/role_templates/:id/cloneClona um papel existente
